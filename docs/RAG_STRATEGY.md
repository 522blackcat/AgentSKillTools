# RAG 分层方案

## 目标

`rag_product` 负责沉淀面向生产项目的知识库能力。你计划分为三类文本长度，这是很好的产品边界，因为文本长度会直接影响切分、召回、上下文压缩和答案组织方式。

## 三类知识库

| 类型 | 文本长度 | 典型内容 | 核心难点 | 推荐策略 |
| --- | --- | --- | --- | --- |
| 短文本 RAG | 1000-5000 字 | FAQ、产品说明、小段业务规则 | 召回要精准，避免过度切分 | 小 chunk 或整文 embedding |
| 中文本 RAG | 5000-30000 字 | 文章、接口文档、项目说明、教程 | 结构化切分和段落上下文 | 标题层级切分 + chunk overlap |
| 长文本 RAG | 30000 字以上 | 书籍、长报告、复杂知识库 | 多跳检索、摘要、章节定位 | 层级索引 + 摘要索引 + 精细块索引 |

## 统一流水线

```text
Document
  │
  ├─ Load
  ├─ Clean
  ├─ Split
  ├─ Embed
  ├─ Store
  ├─ Retrieve
  ├─ Rerank
  └─ Answer with citations
```

## 短文本 RAG

适用场景：

- FAQ。
- 单页产品介绍。
- 小型业务规则。
- 个人笔记卡片。

切分建议：

- 1000-2000 字：整文作为一个 chunk。
- 2000-5000 字：按自然段或标题切成 2-5 个 chunk。
- overlap 控制在 50-100 tokens。

检索建议：

- top_k: 3。
- 优先使用语义相似度。
- 可以保留完整原文作为答案上下文。

验收标准：

- 能回答文档中明确出现的问题。
- 回答能返回来源标题或 chunk id。
- 对文档外问题能明确说“不在当前知识库中”。

## 中文本 RAG

适用场景：

- 技术文章。
- 项目文档。
- 学习资料。
- 中等长度业务制度。

切分建议：

- 优先按 Markdown 标题切分。
- 每个 chunk 约 500-1000 tokens。
- overlap 控制在 100-150 tokens。
- metadata 保留标题路径，例如 `H1 > H2 > H3`。

检索建议：

- 第一阶段向量召回 top_k: 8-12。
- 第二阶段可以用关键词过滤或 rerank 选出 4-6 段。
- 回答时展示引用段落来源。

验收标准：

- 能处理跨段落问题。
- 能引用章节标题。
- 能在召回结果冲突时说明不确定性。

## 长文本 RAG

适用场景：

- 书籍。
- 长篇课程资料。
- 大型产品手册。
- 多文件知识库。

切分建议：

- 建立两层或三层索引：
  - 文档级摘要。
  - 章节级摘要。
  - 段落级 chunk。
- chunk 约 700-1200 tokens。
- 章节摘要作为高层路由，段落 chunk 用于精确回答。

检索建议：

1. 先检索文档/章节摘要，确定范围。
2. 再在目标范围内检索细粒度 chunk。
3. 对多个命中 chunk 做 rerank。
4. 必要时先生成局部答案，再合成最终答案。

验收标准：

- 能回答章节级问题。
- 能回答细节事实问题。
- 能给出引用范围。
- 长文档更新后可局部重建索引。

## 最小可用版本

第一阶段先做一个本地版本：

1. 支持导入 `.txt` 和 `.md`。
2. 根据文本长度自动选择短/中/长策略。
3. 使用 Chroma 或 FAISS 作为本地向量库。
4. 返回答案、引用 chunks、召回分数。
5. 提供一个命令行调试入口。

## 后续优化

- Hybrid search：向量检索 + BM25。
- Reranker：提高召回质量。
- Query rewrite：把口语问题改写成检索友好的查询。
- Parent-child retriever：小块召回，大块注入上下文。
- Evaluation：准备一批标准问题，持续评估命中率和答案质量。
